1. Resumen ejecutivo

El informe v1 dejó la arquitectura, el esquema SQL, los MCP y el BFF listos, pero dos módulos seguían incompletos: el feed del Top 10 y el alta de la primera publicación con autenticación. Esta entrega cierra ese ciclo.

  • Cuenta real: registro e inicio de sesión con Supabase Auth, creación automática del perfil en public.usuarios y sesión compartida entre navegador y Route Handlers mediante @supabase/ssr.
  • Publicación guiada: el diagnóstico local precarga el formulario de /publicar; se sube una portada al bucket portadas y se crean un diagnosticos y un proyectos con consentimiento explícito.
  • Top 10 funcional: ranking semanal, likes, calificaciones de 1 a 5 estrellas y comentarios. La lectura es pública; las interacciones exigen sesión.
  • Revista pública: el visor editorial de 16 páginas sigue abierto a todo el mundo y ahora añade los artículos con estado = 'publicado' desde la base de datos.

La decisión clave fue desacoplar la publicación del MCP: publicar un emprendimiento solo necesita Supabase. La curación editorial con IA y el diagnóstico con LLM siguen siendo opcionales y se activan por separado.

No se dispuso de credenciales de Supabase durante esta entrega. El código, las migraciones y las rutas quedan listas; las pruebas con base de datos real son el siguiente paso del usuario.

3. Arquitectura de la entrega

+----------------+   cookies JWT   +---------------------+   service role   +------------------+
|   Navegador    | <-------------> |  Next.js BFF        | <---------------> | Supabase Auth    |
| RSC + cliente  |   JSON/FormData |  app/api/*          |                 | DB + Storage     |
+--------+-------+                 +----------+----------+                 +------------------+
         |                                   |
         | lectura pública                   | opcional
         v                                   v
 +----------------+                 +---------------------+
 |  /revista      |                 | MCP Curación        |
 |  /top10        |                 | MCP Diagnóstico     |
 +----------------+                 +---------------------+

El BFF sigue siendo el único punto que habla con Supabase y con los MCP. Se añadió lib/config.ts como interruptor: si faltan NEXT_PUBLIC_SUPABASE_URL o NEXT_PUBLIC_SUPABASE_ANON_KEY, las acciones sensibles devuelven un mensaje claro en vez de fallar de forma opaca.

El cliente usa createBrowserClient de @supabase/ssr, de modo que la sesión viaja en cookies y requireUser() puede validarla desde cualquier Route Handler.

5. Flujos implementados

5.1 Registro y sesión

/acceso ofrece dos modos. El registro envía nombre en los metadatos de signUp; el trigger de la migración 0002 crea el perfil en usuarios con rol estudiante. Si el proyecto de Supabase exige confirmación por correo, la UI lo indica y no redirige hasta que exista sesión. El encabezado muestra el usuario y permite cerrar sesión.

5.2 Primera publicación

El formulario de diagnóstico entrega título, descripción, GitHub, stack, puntaje e inglés como query params a /publicar. Tras iniciar sesión, el formulario valida los campos, exige el checkbox de Habeas Data, sube la portada opcional a Storage y ejecuta dos inserciones atómicas desde el BFF: un diagnóstico de origen scoring-local y un proyecto con consentimiento_publicacion = true. Finalmente actualiza la página 5 de la revista en memoria.

5.3 Top 10 y participación

GET /api/proyectos consulta los proyectos con consentimiento, calcula conteos de los últimos 7 días, obtiene el autor y los comentarios, y marca miLike y miEstrellas del visitante. Los botones deshabilitados muestran una invitación a iniciar sesión cuando no hay usuario. Cada acción (like, calificación, comentario) valida sesión y que el proyecto sea público antes de escribir.

5.4 Revista y publicación editorial

GET /api/revista/articulos devuelve únicamente artículos publicado, ordenados por fecha. En el estudio editorial, el botón «Publicar en revista» envía { publicar: true } al PATCH de selección de versión, que cambia el estado y fija published_at. El contenido se muestra como texto plano, sin interpretar HTML.

Las rutas de escritura responden 503 con un mensaje de configuración cuando Supabase no está presente, 401 sin sesión y 403 cuando el rol no corresponde.

7. Seguridad y permisos

  • La service role key solo se usa en servidor; el cliente recibe únicamente la anon key.
  • requireUser() valida la sesión en cada escritura y optionalUser() solo personaliza la lectura.
  • El checkbox de consentimiento es obligatorio en el servidor, no solo en la UI.
  • Se validan tamaño y tipo MIME de la portada (PNG/JPEG/WEBP, máximo 10 MB) y longitud de textos.
  • El contenido generado por IA se muestra como texto plano; no se inyecta innerHTML.
  • RLS existente: diagnósticos privados, proyectos públicos solo con consentimiento, interacciones públicas en lectura y propias en escritura.

Pendiente: rate limiting por usuario, reintento de JSON inválido en completeJson y sanitización con rehype-sanitize si en el futuro se renderiza Markdown como HTML.

9. Puesta en marcha

1. Crear proyecto gratuito en Supabase.

2. SQL Editor, en este orden:
   supabase/migrations/0001_initial_schema.sql
   supabase/migrations/0002_auth_publicacion.sql

3. Authentication > Providers > Email activo.
   Site URL: http://localhost:3000
   Redirect URLs: http://localhost:3000/**

4. cp .env.example .env.local
   NEXT_PUBLIC_SUPABASE_URL=https://XXXX.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
   SUPABASE_SERVICE_ROLE_KEY=eyJ...
   MCP_ALLOWED_HOSTS=XXXX.supabase.co

5. Reiniciar: npm run dev
   Verificar: curl -s localhost:3000/api/proyectos
   Debe devolver "configurado":true

6. /acceso -> crear cuenta -> /publicar -> /top10

7. Para /editor, asignar rol:
   update public.usuarios u set rol = 'editor'
   from auth.users a where a.id = u.id and a.email = 'tu@correo.com';

El MCP y OPENAI_API_KEY no son necesarios para este flujo. Se requieren únicamente para la curación asistida y el diagnóstico con LLM.

10. Estado y deuda técnica

  1. Ejecutar el flujo completo contra un proyecto Supabase real: registro, publicación con imagen, like, calificación y comentario.
  2. Conectar DiagnosticForm a POST /api/diagnostic/analyze para sustituir el scoring local por el reporte del MCP.
  3. Añadir rate limiting por usuario en comentarios, likes y calificaciones.
  4. Sanitizar Markdown con rehype-sanitize si se decide renderizarlo como HTML.
  5. Encolar la curación de documentos largos y notificar por Realtime.
  6. Desplegar MCP en Fly.io/Railway y Next.js en Vercel, con el dominio válido en Auth y CORS.
  7. Persistir la revista en articulos para que el splash de la página 5 sobreviva a una recarga.
