1. Resumen ejecutivo

Se transformó el prototipo estático existente en una base de código de producción con tres capas separadas:

  1. Cliente (Next.js 14): rutas, componentes y formularios.
  2. BFF (Route Handlers): autenticación JWT, validación, persistencia y cliente MCP. Es el único punto que habla con Supabase y con los servidores de IA.
  3. Servidores MCP (Node.js/TypeScript, Streamable HTTP): dos agentes stateless — Curación y Diagnóstico — con tools tipadas con Zod que delegan el razonamiento a un LLM.

El cambio arquitectónico más importante es que el MCP no persiste datos: recibe contenido (o una signed URL), devuelve un objeto validado y el BFF decide qué guardar. Esto permite escalar los MCP horizontalmente, cambiar el proveedor de IA sin migrar datos y sustituir un agente modificando una sola variable de entorno.

Nombre recomendado: Talento Tech Valle como marca paraguas y Revista Tech Valle como marca editorial. Se descarta «Revista Tech» por ser genérico.

  • Navegador → BFF: fetch + Route Handlers.
  • BFF → Supabase: @supabase/ssr para sesión con cookies y service role para operaciones de servidor.
  • BFF → MCP: StreamableHTTPClientTransport con pool por servidor y reintento (lib/mcp-client.ts:48).
  • MCP → LLM: chat.completions con response_format: json_object, validado con Zod. Cliente OpenAI perezoso: el servidor arranca y responde /healthz sin clave.
  • MCP → archivos: los documentos se suben una vez a Storage; el BFF firma URLs con TTL de 5 min y el MCP las descarga. Allowlist opcional MCP_ALLOWED_HOSTS contra SSRF.

3.2 Flujo de curación

  1. El editor sube .docx, .odt o .md (máx. 20 MB) y hasta 5 imágenes.
  2. El BFF valida MIME, tamaño, JWT y rol; guarda en documentos y firma URLs.
  3. curar_contenido extrae texto e imágenes (mammoth / JSZip + fast-xml-parser) y genera n variantes con enfoques conservador, equilibrado y divulgativo.
  4. Cada variante se persiste como fila inmutable; un trigger asigna el número correlativo.
  5. El editor compara con diff LCS en cliente; aprobar actualiza version_activa_id, el contenido y el estado a aprobado.
  6. «Regenerar» añade versiones nuevas sin sobrescribir las anteriores.

3.3 Flujo de diagnóstico

  1. Envío de GitHub, descripción, stack, captura opcional y consentimiento.
  2. El BFF sube la captura a capturas, la firma y llama a analizar_empleabilidad.
  3. El MCP consulta demanda regional (14 tecnologías), obtiene señales de GitHub (stars, lenguajes, README, tests, CI, licencia, último push) y envía la captura al LLM con visión.
  4. El LLM devuelve puntaje, nivel, tecnologías foco, red flags, fortalezas y recomendaciones.
  5. El BFF persiste en diagnosticos y, si el puntaje ≥ 75 hay consentimiento, crea el proyecto postulable al Top 10.

3.4 Decisiones técnicas

DecisiónJustificación
MCP stateless sin BDRéplicas sin sesión pegajosa; separa IA de reglas de negocio y RLS.
Streamable HTTP (2025-06-18)stdio exige proceso local; SSE legacy está en desuso.
Zod en MCP y BFFDoble validación de entradas y de salidas del LLM.
Signed URLs en vez de base64Evita binarios grandes dentro de mensajes JSON.
Numeración por triggerEl historial es inmutable: regenerar nunca sobrescribe.
Service role solo en servidorNinguna credencial privada con prefijo NEXT_PUBLIC_*.
Reporte jsonb + columnas derivadasConserva la respuesta completa y permite consultar campos sin parsear.

4. Detalle de módulos

4.1 Módulo Revista

  • Subida drag & drop con validación (DocumentUploader.tsx).
  • Extracción real de DOCX/ODT/Markdown con imágenes incrustadas.
  • Corrección ortográfica y de redacción, resumen, tags y portada sugerida. Sin imágenes, el LLM devuelve un prompt de portada.
  • Historial con confianza, modelo, prompt version, tags, diff y aprobación (CurationHistory.tsx).
  • Regeneración de 2 versiones adicionales bajo demanda. Ruta: /editor.

4.2 Módulo Diagnóstico

  • demanda_mercado: catálogo versionado con 14 tecnologías, tendencia y salario de referencia.
  • analizar_empleabilidad: calibra 55% stack vs. demanda, 25% calidad evidenciable, 20% captura e inglés; descuenta por red flags confirmadas.
  • Degradación elegante: sin GITHUB_TOKEN, github_signals es null.
  • Endpoint POST /api/diagnostic/analyze con persistencia y postulación condicional.

4.3 Módulo Top 10 Emprendiendo

  • proyectos con consentimiento explícito (Ley 1581) y destacado semanal.
  • likes, calificaciones (1–5) y comentarios con PK compuesta.
  • Vista top10_semanal con security_invoker: ranking de 7 días (likes ×2, comentarios ×3, estrellas ×5).
  • RLS: lectura pública solo con consentimiento; escritura autenticada y propio.
  • PENDIENTE Feed, likes, estrellas, comentarios y Realtime.

7. Seguridad y cumplimiento

  • JWT verificado en cada Route Handler; roles editor/admin en curación.
  • Service role solo en servidor; signed URLs de corta duración para el MCP.
  • Validación Zod en dos capas y allowlist de hosts para descargas.
  • PENDIENTE Sanitización de Markdown (rehype-sanitize) antes de renderizar contenido de IA.
  • Consentimiento explícito de publicación (Habeas Data, Ley 1581 de 2012).
  • Secretos por entorno, nunca logueados ni devueltos al cliente.
