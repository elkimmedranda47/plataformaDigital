1. Resumen ejecutivo

La plataforma quedó con dos flujos principales claramente separados: el flujo editorial, que cura documentos y publica una revista de exactamente 16 páginas, y el flujo de diagnóstico, que analiza un perfil con IA y puede postular proyectos al Top 10.

Editorial

Curación MCP/Gemini a 16 páginas, edición antes de aprobar y publicación explícita.

Diagnóstico

Formulario real conectado al MCP, GitHub, demanda regional y Gemini.

Interfaz

Estilo WIRED aplicado en todo el proyecto: blanco, negro, azul, bordes rectos.

Validación

tsc, lint, build, health MCP y pruebas funcionales OK.

El diagnóstico ya no se queda en scoring local: usa el endpoint real, guarda el reporte en Supabase y muestra fortalezas, red flags, tecnologías a fortalecer y recomendaciones.

3. Flujo del diagnóstico

El formulario Diagnóstico de Competitividad Junior (Valle del Cauca) hace este recorrido:

  1. Entrada del estudiante. /diagnostico valida nombre, título del proyecto, URL de GitHub, nivel de inglés, stack, descripción de al menos 20 caracteres, captura opcional y consentimiento de publicación.
  2. Petición autenticada. El cliente envía POST /api/diagnostic/analyze. El BFF ejecuta requireUser(); sin sesión responde 401 y la UI muestra enlace a /acceso.
  3. Captura. Si hay imagen, se sube al bucket capturas de Supabase y se pasa una URL firmada de corta duración al MCP.
  4. Herramienta MCP. El BFF invoca analizar_empleabilidad en http://localhost:3002/mcp mediante lib/mcp-client.ts.
  5. Contexto objetivo. El MCP consulta señales públicas de GitHub (stars, forks, README, tests, CI, licencia, último push, lenguajes) y el catálogo DEMANDA_VALLE.
  6. IA y normalización. Gemini responde JSON; normalizarReporte() corrige alias y límites antes de que Zod valide el esquema.
  7. Persistencia. El BFF inserta el reporte en diagnosticos. Si postulable_top10 es true y hay consentimiento, crea el registro en proyectos para el Top 10.
  8. Resultado. La UI muestra puntaje, nivel, resumen, fortalezas, tecnologías a fortalecer, red flags, recomendaciones y señales de GitHub. Si aplica, publishSplash actualiza la página 5 de la revista local.
/diagnostico
  -> POST /api/diagnostic/analyze (sesion + captura opcional)
     -> MCP diagnostico :3002/mcp
        -> GitHub: senales objetivas del repo
        -> demanda.ts: catalogo DEMANDA_VALLE
        -> Gemini: JSON del reporte
        -> normalizarReporte + Zod
     -> INSERT diagnosticos
     -> INSERT proyectos si postulable_top10 y hay consentimiento
  -> UI: reporte real + splash en pagina 5

5. Error corregido: nivel “junior”

Síntoma: el modelo devolvió "nivel": "junior", pero el esquema del tool solo aceptaba inicial, intermedio o avanzado. Zod rechazó la respuesta con invalid_enum_value.

Solución:

  • Se añadió normalizar() en mcp/shared/src/llm.ts, aplicada antes de validar con Zod.
  • Se creó normalizarReporte() en mcp/diagnostic/src/index.ts.
  • Alias mapeados: junior/inicial/básico/beginner/entry → inicial, intermedio/mid → intermedio, senior/avanzado/expert → avanzado.
  • Si el valor no es reconocido, se infiere del puntaje: menor a 60 inicial, 60-84 intermedio, 85 o más avanzado.
  • También se limitan arrays y textos para que una respuesta larga del modelo no rompa el esquema.
  • El prompt ahora pide literalmente inicial, intermedio o avanzado.
Prueba posterior: diagnóstico real completado con nivel: intermedio, puntaje: 85, postulable_top10: true y señales de GitHub obtenidas correctamente.

6. Flujo editorial y estados

AcciónQué haceQué no hace
Editar y aprobarAbre modal, guarda título, resumen, tags, portada y contenido en la versión; deja el artículo en aprobado.No cambia estado a publicado ni escribe published_at.
Publicar en revistaCopia la versión activa al artículo, pone estado='publicado' y escribe published_at.No elimina automáticamente otra editorial publicada.
Publicar segunda editorialAmbos artículos quedan publicados; el visor toma el más reciente por published_at desc.No despublica al anterior; hay que usar Quitar de revista si se desea.

Comportamiento con documentos largos

Si el documento trae 24 páginas con hojas en blanco, el extractor descarta los fragmentos vacíos. El curador fuerza exactamente 16 páginas y el prompt pide comprimir sin perder secciones clave. Las tablas se extraen como texto: su información se conserva en la medida en que entra al prompt, pero el formato visual puede aplanarse. El contenido enviado al modelo se corta en 24.000 caracteres, por lo que conviene revisar tablas críticas en el modal Editar y aprobar.

7. API key de Google AI Studio

No hace falta crear otra API key para el diagnóstico. La plataforma usa una sola key en OPENAI_API_KEY con OPENAI_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/. Tanto mcp/curation como mcp/diagnostic llaman a Gemini a través de esa configuración.

Puedes crear una segunda key solo si quieres separar cuotas, presupuesto o permisos por agente. En ese caso, define una variable adicional para diagnóstico y cámbiala en mcp/shared/src/llm.ts; después reinicia ambos MCP y el servidor Next.

Si rotas la key: actualiza .env.local, reinicia los MCP y reinicia npm run dev. No se debe imprimir ni commitear la key.

8. Pendientes y recomendaciones

  • Rotar la service role key antigua y cualquier key de Gemini que haya quedado expuesta.
  • Para deploy público, migrar los MCP de localhost a servicios accesibles y configurar MCP_CURACION_URL y MCP_DIAGNOSTICO_URL.
  • Actualizar DEMANDA_VALLE con una fuente periódica si se quiere que el diagnóstico refleje convocatorias reales.
  • Probar RLS con dos usuarios para confirmar que un estudiante no ve diagnósticos ajenos.
  • Si se desea una sola editorial visible, hacer que Publicar marque la anterior como aprobado antes de publicar la nueva.
